## 三、核心架构决策

### 3.1 子应用怎么"安装"：把静态目录挂到一个本地 origin

**不能用 `file://`。** Android WebView 在 `file://` 下禁止 ES module（CORS），`fetch`、`localStorage`、Worker 也都不正常。子应用一旦要长成真应用，`file://` 死路一条。

**做法**：宿主把子应用的静态文件目录，通过一个**本地 origin** 暴露给 WebView。

| 端 | 机制 | 子应用看到的 URL |
| --- | --- | --- |
| Android | `WebViewAssetLoader` | `https://appassets.androidplatform.net/apps/msglist/index.html` |
| macOS / iOS | `WKURLSchemeHandler` | `moechat-app://apps/msglist/index.html` |
| Web 宿主 | 同源路径 | `/apps/msglist/index.html` |
| 开发（浏览器） | 任意静态服务器 | `http://localhost:8080/` |

这样：ES module 能用、`fetch` 能用、`localStorage` 按 origin 隔离（每个子应用一个 origin，天然沙箱），且**离线可用**。

**「安装」= 把子应用的静态目录复制进宿主的资源目录。** 不是下载、不是联网。

| 端 | 安装落点 |
| --- | --- |
| Android | `app/src/main/assets/apps/msglist/`（构建时复制，该路径 gitignore） |
| macOS | `Moechat.app/Contents/Resources/apps/msglist/`（`make-app.sh` 里复制） |

### 3.2 子应用怎么"启动"：宿主的子应用清单里加一条

宿主现在把子应用写死在代码里（macOS `Quadrant.swift:31`、Android `Models.kt:30`）。加一个字段：

```swift
SubApp(id: "chat", title: "消息", symbol: "bubble.left", entry: "apps/msglist/index.html")
```

点击子应用 → 宿主按自己的 origin 拼出 URL → 加载。各端 origin 不同，**子应用代码里不出现任何 origin 假设**（全部用相对路径）。

### 3.3 子应用技术栈：Vite + TypeScript + React

| 选项 | 取舍 |
| --- | --- |
| 原生 ES module，零依赖无构建 | 简单、无供应链；但 3D 人体子应用迟早要 three.js + 打包器，两套约定并存更差 |
| **Vite + TypeScript + React**（已定） | 生态齐全、类型防漂移、AI 生成可靠；代价是引入构建步骤 |

**为什么是 React 而不是 Vue/Svelte**（长期视角）：

1. **后续子应用要用的东西，React 生态最全**——3D 人体要 `react-three-fiber`；聊天要虚拟滚动（`TanStack Virtual`，几万条消息不卡）、Markdown 渲染、图片/视频查看器、手势库。Vue 有对应物但薄一档，Svelte 更薄。
2. **AI 写 React/TS 的可靠性明显更高**——本项目基本由 AI 写代码，训练数据量差异直接变成产出质量差异。
3. **TypeScript**：子应用会越来越多，还要共用一套设计令牌。类型是防四端漂移的第一道闸。
4. **Vite 的 `base: './'`** 正好产出相对路径资源，正是宿主契约要的「不假设 origin」。

**注意**：宿主契约是「一个静态目录」，与子应用是否构建**无关**。选了构建器，宿主侧一行都不用改——安装的是 `dist/` 而不是 `src/`。

### 3.4 多语言：类型化文案目录，编译期拦截硬编码

**要求**：多语言支持，**删除 hardcode**（需求方 2026-09-25）。

**做法**：不用 i18n 库，用 TypeScript 目录 + `Intl` 内建。

```
src/i18n/
├── index.ts          t() / setLocale() / 当前 locale 状态
└── locales/
    ├── zh-Hans.ts    基准目录 —— 键的类型由它推导
    └── en.ts         其余语言：缺键 = 编译错误
```

```ts
// locales/zh-Hans.ts
export const zhHans = {
  'conversation.empty': '还没有会话',
  'chat.placeholder': '输入消息…',
} as const;

// locales/en.ts
export const en: typeof zhHans = {   // ← typeof 基准目录
  'conversation.empty': 'No conversations yet',
  'chat.placeholder': 'Type a message…',
};
```

**为什么不用 i18n 库**：

- 主流库的键是 `string`，**拼错键名只在运行时发现**（界面显示成 `chat.plaeholder`）。用 `typeof` 基准目录，**缺翻译、拼错键名、多写键都是编译错误**。这是「删除 hardcode」最硬的执行手段——比 code review 可靠。
- 零依赖、零运行时开销。

**配套硬规则**：

1. **组件里不出现任何面向用户的字面量**，一律 `t('key')`
2. **日期/时间/数字一律走 `Intl`**（`Intl.DateTimeFormat` / `Intl.RelativeTimeFormat`），禁止手工拼 `"昨天"`、`"13:07"`
3. 复数用 `Intl.PluralRules`（中英文都不需要，先不引入，留接口）
4. locale 来源：`window.moechat.locale` → 取不到则 `navigator.language` → 再不行 `zh-Hans`
5. 兜底链：`zh-Hans-CN` → `zh-Hans` → `zh` → 基准目录

**将来要 ICU（复数/性别/选择）时**，在 `t()` 内部换成 `@formatjs/intl-messageformat` 即可，调用方一行不用改。

**本期不做**：语言切换 UI（locale 由宿主给）、RTL 布局、消息内容的翻译。

### 3.5 配色：子应用沿用宿主同一套令牌

宿主已有统一配色（`Theme.swift` / `Theme.kt`，两边逐值相同）。子应用**不自己发明一套**，把相同取值写进 CSS 变量，顶部注明「取自《宿主设计实现方案》§3.1，四端同源同值」。

将来若要让宿主运行时下发配色，扩展 `window.moechat` 即可，本期不做。


- 单人：对端名称，消息不带发送者名

- 底部输入区（纯渲染，不发送）

**不做**（本期）：真实收发、登录、后端、已读回执、消息搜索、附件、语言切换 UI（locale 由宿主给）、RTL 布局。

### 5.5 宿主多语言（需求方 2026-09-25 追加：**包括宿主 app**）

**现状**：两端宿主各有约 15 条硬编码中文文案。

| 位置 | 文案 |
| --- | --- |
| 顶栏 | 切换主体、时空坐标、后退、前进、刷新 |
| 象限名 | 肉体、知识、关系、持有物 |
| 子应用名 | 人体、消息、收藏、第三象限那个、资产 |
| 占位页 | 「Web 子应用占位 · 将由 … 提供」「宿主上下文读取中…」「主体 / 时空 / 主题」 |

**顺带修一处跨端不一致**：macOS 第三象限叫「关系」+「人际」，Android 叫「关系」+「社会关系」。按已确认的结论统一为 **社会关系**。

**做法：各端用各自的原生资源机制**，不搞跨仓库共享文案源。

| 端 | 机制 |
| --- | --- |
| Android | `res/values/strings.xml`（基准）+ `res/values-en/strings.xml`；`Quadrant`/`SubApp` 的 title 由 `String` 改为 `@StringRes Int`，展示处用 `stringResource()` |
| macOS | SwiftPM 本地化资源：`Package.swift` 加 `defaultLocalization`，`Sources/Moechat/Resources/{zh-Hans,en}.lproj/Localizable.strings`，取值用 `String(localized:bundle:.module)` |

**不共享文案源的理由**：宿主文案量小且稳定（约 15 条），子应用文案量大且独立演进（msglist 一开始就有几十条）。强行合并成一个跨仓库文件，代价（生成步骤、格式转换、同步时机）大于收益。**但键名两端保持一致**（`quadrant.first`、`app.chat`、`topbar.back`…），便于日后比对是否漏翻。

**基准语言 = zh-Hans**；系统语言不支持时回落到它。

**locale 怎么传**：宿主取系统语言，写进 `window.moechat.locale`，子应用按自己的兜底链解析。

| 端 | 取值 | 示例 |
| --- | --- | --- |
| Android | `Locale.getDefault().toLanguageTag()` | `zh-Hans-CN` |
| macOS | `Locale.current.identifier`，下划线换成连字符 | `zh-Hans-CN` |

统一成 BCP-47（连字符），因为 macOS 的 `identifier` 给的是 `zh-Hans_CN`，两种写法会让子应用侧多写一套兼容。

**本期不做**：RTL、宿主内的语言切换 UI（跟随系统）、日期本地化（宿主只显示一个时空坐标字符串）。

## 八、已知风险

| 风险 | 应对 |
| --- | --- |
| macOS 无 Xcode（技术选型文档记录），只有 CommandLineTools | `swift build` 可编译 SwiftUI；运行靠 `make-app.sh` 打 bundle。第 3 期若跑不起来，改用 `swift run` 验证 |
| Android 老设备 WebView 不支持 documentStart 注入 | 保留 `onPageStarted` 降级路径 |
| 两端 origin 不同（https vs 自定义 scheme） | 子应用只用相对路径，不写绝对 URL。第 1 期的浏览器调试用 localhost，正好逼出这个问题 |
| 宿主仓库里出现子应用文件的副本 | 复制目标路径全部 gitignore，副本永不入库 |
| SwiftPM 本地化资源容易踩坑 | 需要 `Package.swift` 的 `defaultLocalization` 与 `.process("Resources")` 同时到位，否则 `.lproj` 不被打进 bundle，中英文都不生效。第 3 期先单独验证一次本地化资源能否加载，再接子应用 |
| 「删除 hardcode」会反复退化 | 子应用侧由 TypeScript 类型兜底（漏键=编译错误）；宿主侧无此机制，靠验收时 `grep` 中文断言。写进两端的 README 作为约定 |

### 关键设计

- **子应用目录不进仓库**。`syncSubApps` 的产物落在 `build/generated/assets/`（已被 `.gitignore` 覆盖），
  assets 里没有第二份 msglist 副本。未构建时 `syncSubApps` 直接 `GradleException` 并打印该跑哪条命令，
  不留「文件不存在」这种无头绪的报错。
- **JS 契约四端一致**。Android 的 `@JavascriptInterface` 只能收 String，
  于是把 stringify 塞进 `bootstrapScript` 的 JS 层，JS 侧看到的仍是
  `window.moechatHost.post(type, payloadObject)`，与 macOS 的 `webkit.messageHandlers` 版本完全同形。
  差异只存在于宿主适配层。
- **宿主不碰子应用内部**。WebView 设置全部取标准值，没有为了绕过子应用的布局 bug 而加宿主配置——
  子应用要在四端都站得住，不能靠某一端兜。
- **`values/` 当 zh-Hans 基准**，任何未支持的语言自动回落到中文；`values-en/` 是英文。
  标题字段用 `@StringRes Int` 而不是 `String`，改动一处编译器会点名所有漏改的调用点。

### 过程中定位的真问题：WebView 里 html 的盒子高度是 0

Android WebView 实测（容器 1080×1812px，dpr 2.625）：

| 量 | 值 |
| --- | --- |
| `innerHeight` | 691 |
| `document.documentElement.clientHeight` | 691 |
| `document.documentElement.getBoundingClientRect().height` | **0** |
| `body.clientHeight` | **0** |
| `#root.clientHeight` | **0** |

`html { height: 100% }` 在这里得到 0，`height: 100%` 逐级传下去全是 0，
`overflow: hidden` 把滚动容器剪成空白。症状极具误导性：标题（被 flex 溢出撑出来）看得见，
列表整片空白，且 `documentElement.clientHeight` 按规范恒等于视口，量它永远「正常」。

修在**子应用**侧（`.app { position: fixed; inset: 0 }`），不是宿主侧——
这是子应用自己的布局前提，四端都要成立。
